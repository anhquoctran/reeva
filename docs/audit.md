# Reeva audit

Scope: repository source, migrations, views, package/build configuration, and the SQLite setup visible in the repository. This is an application audit; it does not prove the deployed environment is secure.

## Confirmed findings

| ID | Severity | Status | Evidence and impact | Resolution |
| --- | --- | --- | --- | --- |
| R-001 | P1 | Confirmed | `start/routes.ts` served arbitrary local paths assembled from a wildcard key without containment or symlink checks. A request could read files outside the configured storage root. | Fixed with canonical root containment, symlink resolution checks, regular-file checks, and public-artifact eligibility. |
| R-002 | P1 | Confirmed | `UpdaterService.recordAndStream` used `Artifact.findOrFail(id)` without checking publish, archive, version activity, or related soft-deletes. A known draft/archived/inactive release ID could be downloaded. | Fixed by a shared public-artifact query used by check/latest/releases/download/local file serving. |
| R-003 | P1 | Confirmed | `ArtifactService.uploadArtifact` read the complete upload into RAM, wrote a deterministic storage key before inserting the row, and did not remove the object if the DB insert failed. Repeating the same version/platform/architecture/channel overwrote the existing binary before the DB uniqueness constraint rejected the row. | Fixed with streamed provider APIs, `artifacts/<reservation UUID>/payload` keys, transactional quota reservations, DB-failure compensation, and retry cleanup of expired reservations on the next upload to that provider. |
| R-004 | P1 | Confirmed | CMS routes required only an active session. `isRoot` was checked for a few user mutations but not enforced for user, storage-provider, or global-settings administration. | Fixed by a root-only middleware on those route groups and the underlying self/root mutation checks. |
| R-005 | P1 | Confirmed | Artifact details JSON serialized the preloaded `storageProvider` model, including its `config` field with access and secret keys. | Fixed with an explicit artifact/history DTO that omits provider config and credentials. |
| R-006 | P1 | Confirmed | Password reset tokens were stored in plaintext and token lookup/password update/token deletion were separate operations. Concurrent reset posts could replay the token; password changes did not revoke active sessions or remember-me tokens. | Fixed by hashing newly issued tokens, transactional single-use consumption, legacy-token compatibility during its one-hour expiry, a per-user auth version checked on every CMS request, and deletion of persistent tokens on password changes. Existing sessions without the version are logged out at upgrade. |
| R-007 | P2 | Confirmed | Login and password-reset posts had no abuse throttling. | Fixed with a database-backed bounded-window limiter shared across instances. |
| R-008 | P2 | Confirmed | `RealIpMiddleware` trusted client-supplied forwarding headers while `trustProxy` was enabled globally, allowing IP attribution/location controls to be spoofed. | Fixed by using the socket peer address unless proxy trust is explicitly configured at the HTTP server boundary. |
| R-009 | P2 | Confirmed | Download requests synchronously called an HTTP geolocation service without a timeout; a network failure could hold the OTA response open. The free endpoint also lacks HTTPS and is not permitted for commercial use. | Fixed by removing the third-party lookup from the download path. Existing geo columns remain; new history rows store null location until a suitable licensed HTTPS source is configured. |
| R-010 | P2 | Confirmed | API parameters were read from `request.all()` without format/range validation; bad page sizes, channels, and semantic versions reached query logic, and many exceptions were returned as 404. Download URL origin came from the untrusted Host header. | Fixed with explicit API input validation, bounded pagination, correct 400/404/503 semantics, and the configured `APP_URL`. |
| R-011 | P2 | Confirmed | Dashboard chart SQL used `HOUR(created_at)`, which SQLite does not implement. Dashboard health could also throw on storage query errors after detecting a DB failure. | Fixed with dialect-neutral date bucketing and independent health checks. |
| R-012 | P2 | Confirmed | The project had mutually inconsistent package-manager instructions: two lockfiles, Docker/Yarn, README/npm, and pnpm workspace/override configuration. pnpm 11 ignored the manifest-level override. | Fixed by selecting pnpm, pinning its version, moving overrides to workspace config, updating docs and Docker, and retaining the user's `yargs-parser` 22.0.0 lockfile change while regenerating dependency resolutions. |
| R-013 | P2 | Confirmed | Multipart parsing allowed 1 GiB requests and the application created a second full-size in-memory copy. The app-level copy is removed; the existing request size ceiling remains for compatibility. | Fixed streaming removes the RAM amplification. The 1 GiB parser ceiling is retained and still requires deployment-level request/disk capacity controls. |
| R-014 | P2 | Confirmed | `StorageProvider` and several aggregate/raw/join queries did not consistently account for soft-deleted related rows. Public API joins in particular could include soft-deleted versions/platforms/architectures. | Fixed in the shared eligibility query. General CMS aggregates retain rows where storage objects still exist, as documented. |
| R-015 | P2 | Confirmed | Seeder configuration used a developer-specific absolute Windows path and included public demo storage credentials; `.env.example` had a malformed SMTP variable. | Fixed to use a local relative storage path, inert placeholders, and corrected environment documentation. |
| R-016 | P2 | Confirmed | Production container installed dependencies with Yarn even though the application declares pnpm workspace settings; it copied the source package manifest without an explicit runtime build verification. | Fixed to use the selected pnpm lockfile and include runtime metadata required for ESM aliases. |
| R-017 | P3 | Confirmed | Baseline lint reported 181 errors; the test command executed zero test cases. | Lint is cleaned and 17 focused regression tests now execute; see verification status for infrastructure limits. |
| R-018 | P1 | Confirmed | On SQLite, Lucid replaced newly generated UUID model IDs with numeric `rowid` values because UUID models did not self-assign primary keys. Dependent artifact inserts then failed their foreign keys; newly created records could also return an ID that did not identify the persisted row. | Fixed `selfAssignPrimaryKey` on all UUID-backed models and covered model creation plus dependent upload operations in SQLite tests. |
| R-019 | P2 | Confirmed | The first database-backed auth limiter incremented both IP and identity keys on every request. After the IP threshold, an attacker could still add unbounded one-off identity rows from one source IP. | Fixed by stopping after the IP counter is over limit; regression test sprays unique identities and verifies key creation stops at the IP threshold. |
| R-020 | P2 | Confirmed | CMS semantic-version filters parsed up to 50 digits into query parameters and accepted comparator-plus-wildcard forms such as `>=1.2.*` as equality filters. Oversized input could produce database errors; wildcard input could silently return wrong versions. | Fixed by limiting each numeric part to the supported nine digits and rejecting wildcard comparators. |
| R-021 | P2 | Confirmed, SQLite-specific unresolved deployment check | `migration:reset` on a temporary SQLite database fails in an old table-rebuild migration while foreign keys are enabled. The new additive migration rolls back successfully on both SQLite and MySQL. | Historical migrations were left intact. Use a verified database backup to roll back a deployment; the full historical reset path was not tested on MySQL and is not a deployment rollback procedure. |
| R-022 | P1 | Confirmed, fixed | The production container failed during module loading: MinIO 8.0.7 eagerly imported a case-sensitive `stream-json/jsonl/Parser.js` path and called the v1 `.make()` API, while the security override resolved stream-json 3.x. The app could not start even when MinIO was not selected. | Added a narrow MinIO notification-parser patch using Node's `readline` and JSON parsing, pinned via pnpm patchedDependencies. Docker copies the patch into both dependency stages; rebuilt-container HTTP smoke verifies runtime startup. |
| R-023 | P1 | Confirmed, fixed | Software identity was implicit and global: the database enforced one global semantic-version tuple, CMS version/artifact views had no product boundary, and public OTA selection had no product scope. Adding another application would collide on versions or mix release selection/downloads. | Added a `software` table and additive backfill, scoped version uniqueness, root-managed product lifecycle, product-aware CMS/API responses, and software-scoped download eligibility. Legacy OTA routes continue to resolve the active default product. |
| R-024 | P1 | Confirmed, fixed | The production server rendered CMS templates relative to the build directory while the Vite manifest was resolved relative to the repository root. `/login` returned HTTP 500 with `Missing manifest file`, blocking both login and CMS pages in the built runtime. | Vite now resolves its manifest through the application root. `pnpm verify:production-smoke` launches the compiled server against fresh temporary SQLite and asserts login and CMS pages render. |
| R-025 | P1 | Confirmed, fixed | AuthFinder hashes the mapped password column when saving a user, but create/reset/change-password and root seeding also pre-hashed values. The stored hash was therefore a hash of a hash; credentials returned by account creation/reset and the configured root login did not authenticate. | Password-writing paths now provide plaintext only to the model save hook. Regression tests authenticate against the resulting password after concurrent reset attempts; the production smoke test also signs in the seeded root account. |

## Trigger and root-cause notes

| Finding | Trigger, reproduction, root cause, and affected flow |
| --- | --- |
| R-001 | A path key containing parent segments or an artifact key resolving through a symlink could escape the local root. The old provider joined unchecked input with the root. Reproduced with traversal strings and a symlink; local file downloads are the affected flow. |
| R-002 | A client knowing an artifact UUID could request `/api/download/:id` for a draft, archived, inactive-version, or soft-deleted release. The ID lookup bypassed public lifecycle rules; all public release endpoints and local serving were affected. |
| R-003 | Uploading a second file for the same release tuple overwrote the deterministic object key before the duplicate DB insert failed; a DB failure after a new object write could also orphan the object. Storage and DB had no coordinated key/compensation protocol. |
| R-004 | Any active CMS session could visit user, provider, or settings screens because routes relied on login only; selected controller checks did not form a route-wide role boundary. These administrative screens expose account and global configuration changes. |
| R-005 | Opening artifact details with a provider preloaded caused Lucid model serialization to include the provider config object. This could disclose storage access credentials to an authenticated CMS response consumer. |
| R-006 | Reusing a reset link concurrently or after password change could race separate token/password writes; plaintext tokens were stored and active sessions were not revoked. The reset transaction and session lifecycle were the root cause. |
| R-007 | Repeated login or reset requests had no shared throttle. Multiple application instances could receive an unbounded stream of password guesses and reset work. |
| R-008 | Supplying `X-Forwarded-For` or similar headers could change the observed client IP even without a configured trusted proxy. The global proxy trust setting made client metadata spoofable. |
| R-009 | A slow or unavailable geolocation endpoint could stall an OTA download, and the selected free endpoint used plain HTTP and had commercial-use restrictions. The network call was synchronous in the download request path. |
| R-010 | Invalid semantic versions, channels, page values, or IDs reached query/service code; exceptions were broadly mapped to not-found responses, and generated URLs could use a hostile Host header. Input validation and origin selection were inconsistent at the HTTP boundary. |
| R-011 | Opening the dashboard on SQLite executed unsupported `HOUR(created_at)` SQL; health reporting could also throw after a database probe failed. The query assumed MySQL syntax and coupled checks. |
| R-012 | Clean installs could not follow one reproducible toolchain because npm/Yarn/pnpm instructions and lockfiles diverged; pnpm 11 reads overrides from workspace config. Verified with frozen installs and the Docker dependency stages. |
| R-013 | A large multipart upload was parsed up to 1 GiB and then copied into a full Buffer, so concurrent uploads multiplied resident memory by file size. The parser-to-service boundary duplicated bytes. |
| R-014 | Raw joins/aggregates and related rows could treat a soft-deleted version, target, or provider as live. Soft-delete scopes were not a universal SQL constraint; public eligibility now explicitly accounts for each relation. |
| R-015 | Running seeders on a different host could target a developer-specific absolute path and introduce demo credentials. The seed/config defaults were environment-specific and unsafe to reuse. |
| R-016 | A production image built around Yarn and source-style aliases did not match the pnpm workspace/runtime package contract. Clean Docker build and startup were the reproducer; the MinIO/stream-json incompatibility was a separate, later-confirmed runtime blocker tracked as R-022. |
| R-017 | The baseline test command exited without executing cases while lint reported 181 errors. This left the risky HTTP, auth, storage, and migration behavior without regression evidence. |
| R-018 | Creating a UUID model on SQLite could persist an integer rowid instead of the UUID, causing dependent foreign keys to fail or returned IDs not to identify rows. UUID models lacked Lucid's `selfAssignPrimaryKey` setting. |
| R-019 | After an IP exceeded its throttle window, sending fresh email identities still inserted one DB key per request. Incrementing the identity key after the IP rejection allowed unique-key storage growth. |
| R-020 | A long numeric semver component could overflow database assumptions, and `>=1.2.*` was treated as a comparator equality filter. The filter parser accepted constructs inconsistent with version creation. |
| R-021 | Running a full rollback/reset against disposable SQLite reaches a historical table rebuild that drops a referenced table with foreign keys enabled. This is a migration-history issue and remains unresolved pending a safe history-compatible approach. |
| R-022 | A clean production container failed at startup even if MinIO was not configured because its package module statically imported a stream-json 1.x path/API while the patched dependency graph selected safe stream-json 3.x. The production dependency graph could not load; the narrow notification parser patch was exercised by final image startup and HTTP smoke. |
| R-023 | Products had no first-class row or stable identifier, so version uniqueness and public candidate selection were global. The data model, CMS forms, generated artifact names, and API routes shared singleton assumptions; migration backfills all historical versions to the compatibility product and all public queries carry an explicit software scope. |
| R-024 | Running the compiled server from its build directory made the relative manifest path point under the wrong root; template rendering could not find the asset manifest. The path base differed between development and production runtime. |
| R-025 | Password writes manually called the hashing service and assigned the result to `passwordHash`, which AuthFinder treats as plaintext and hashes again in its save hook. Account creation, password changes/resets, and the seeded root were affected. |

## Investigated, not confirmed as a vulnerability

- Local path traversal is confirmed; exploitation of a symlink planted by a local OS-level writer is mitigated by canonical resolution but remains subject to filesystem TOCTOU if an attacker can concurrently mutate the storage tree.
- No client-controlled remote URL is fetched by the OTA API, so SSRF was not identified in the inspected request paths.
- CSRF is enabled for browser write methods and upload forms include CSRF tokens. CSP is disabled, and a CMS view loads Ace from a CDN; this is a hardening/availability concern rather than a reproduced injection bug.
- API checksum fields are computed from uploaded bytes. The server does not sign releases or verify signatures on the client; cryptographic OTA authenticity remains a client contract and deployment key-management decision.
- Quota checks reserve capacity transactionally. A process termination after object write leaves an expiring reservation; the next upload to that provider retries deletion using the reservation UUID. If that provider is never used again or remains unavailable, the object can persist until storage lifecycle/operator cleanup.

## Access policy applied

- Unauthenticated OTA clients can call check/latest/releases and download eligible public artifacts.
- Any active authenticated CMS user can manage versions and artifacts, including publication. Root users additionally manage accounts, storage-provider credentials, and global settings. This follows the existing `isRoot` boundary; the repository has no finer-grained role model.
- Self-profile and password changes are available to the authenticated user. Inactive users and sessions with an old auth version are rejected.
- Soft-deleting an artifact retains its object and quota usage. Archive removes it from public eligibility while retaining the object.

## Environment and dependency limits

- The checked-in test suite initially contained only `tests/bootstrap.ts`; the baseline test command reported `NO TESTS EXECUTED`.
- A disposable MySQL 8.4.11 service was started with synthetic credentials and a randomly named temporary schema. Fresh migration, additive down/reapply, legacy user preservation, remember-me token revocation, foreign key creation, and the MySQL public-release index branch passed. MySQL request-level query/concurrency behavior and production configuration were not tested.
- Dependency advisories, SQLite/MySQL migration checks, and container build/runtime are recorded in `docs/verification.md` with exact commands and limits.
- S3, MinIO, SeaweedFS, SMTP, reverse-proxy behavior, and cloud IAM remain unverified without those services. MySQL checks cover schema upgrade behavior, not a full production-like dataset or all query plans.
