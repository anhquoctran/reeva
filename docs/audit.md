# Reeva audit

Scope: repository source, migrations, views, storage providers and package/build/deployment configuration. Current runtime support is **PostgreSQL only**. Earlier SQLite/MySQL evidence below describes the historical baseline and does not claim current backend support. This application audit does not prove a deployed environment is secure.

## Finding evidence and regression map

### OTA signing follow-up (2026-10-08)

- **R-038 — P1, confirmed; server mitigation implemented, client enforcement
  outstanding.** The baseline `app/services/updater_service.ts` exposed hashes
  without an authenticated release manifest. An attacker able to replace both
  server metadata and binaries could replace the hash as well. Public-key
  registration and exact Ed25519 manifests now bind software/version/channel,
  target, hash and size. `app/services/ota_release_signature_service.ts`,
  `artifact_service.ts` signature submission/publication, and
  `artifact_repository.ts` public eligibility share the policy. A verified JSONB
  snapshot must equal current metadata in SQL; stale signature-save races and
  related version/target renames cannot restore signed-only eligibility. Reeva cannot
  prove authenticity to a client that ignores the signature or trusts keys
  obtained from the same compromised server. No client source exists here;
  pinned-key validation and rollback/freshness protection remain explicit
  integration conditions. Regression tests reject stale/foreign/revoked keys
  and unsigned publication under the signed-only policy.
- **R-039 — P2, confirmed vulnerable dependencies; fixed.** The lock contained
  `proxy-addr@2.0.7`, `source-map-js@1.2.1`, and `fast-copy@4.0.3` covered by
  current advisories. Proxy bypass requires a problematic IPv4-mapped IPv6
  trusted-prefix configuration; the other advisories require malicious source
  maps or excessively deep copy input. No successful remote exploitation of
  Reeva was established. Minimum overrides and the lock now resolve 2.0.8,
  1.2.2 and 4.1.2 respectively. Regression tests exercise proxy-prefix rejection
  and bounded copy depth; dependency verification passes. Sources:
  [proxy-addr](https://github.com/advisories/GHSA-jqcg-44mw-7w3h),
  [source-map-js](https://github.com/advisories/GHSA-68fv-2mgg-jv7q),
  [fast-copy](https://github.com/advisories/GHSA-jggr-w7fw-pc2j).

The new Rust signer separates requester, approver and vault operator credentials,
checks the signed provider response independently, and commits audit/result
before returning a signature. Real OpenBao/PostgreSQL tests cover export denial,
expiry, retry, DB failure after signing and seal/restart behavior. This does not
establish absolute key secrecy: host administrators, compromised unsealed
OpenBao, or a compromised authorized signer remain in the trust boundary. See
[signer operations](signer-operations.md) for custody and production limits.

## Trigger and root-cause notes

| Finding | Trigger, reproduction, root cause, and affected flow                                                                                                                                                                                                                                                                                                                    |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-001   | A path key containing parent segments or an artifact key resolving through a symlink could escape the local root. The old provider joined unchecked input with the root. Reproduced with traversal strings and a symlink; local file downloads are the affected flow.                                                                                                   |
| R-002   | A client knowing an artifact UUID could request `/api/download/:id` for a draft, archived, inactive-version, or soft-deleted release. The ID lookup bypassed public lifecycle rules; all public release endpoints and local serving were affected.                                                                                                                      |
| R-003   | Uploading a second file for the same release tuple overwrote the deterministic object key before the duplicate DB insert failed; a DB failure after a new object write could also orphan the object. Storage and DB had no coordinated key/compensation protocol.                                                                                                       |
| R-004   | Any active CMS session could visit user, provider, or settings screens because routes relied on login only; selected controller checks did not form a route-wide role boundary. These administrative screens expose account and global configuration changes.                                                                                                           |
| R-005   | Opening artifact details with a provider preloaded caused Lucid model serialization to include the provider config object. This could disclose storage access credentials to an authenticated CMS response consumer.                                                                                                                                                    |
| R-006   | Reusing a reset link concurrently or after password change could race separate token/password writes; plaintext tokens were stored and active sessions were not revoked. The reset transaction and session lifecycle were the root cause.                                                                                                                               |
| R-007   | Repeated login or reset requests had no shared throttle. Multiple application instances could receive an unbounded stream of password guesses and reset work.                                                                                                                                                                                                           |
| R-008   | Supplying `X-Forwarded-For` or similar headers could change the observed client IP even without a configured trusted proxy. The global proxy trust setting made client metadata spoofable.                                                                                                                                                                              |
| R-009   | A slow or unavailable geolocation endpoint could stall an OTA download, and the selected free endpoint used plain HTTP and had commercial-use restrictions. The network call was synchronous in the download request path.                                                                                                                                              |
| R-010   | Invalid semantic versions, channels, page values, or IDs reached query/service code; exceptions were broadly mapped to not-found responses, and generated URLs could use a hostile Host header. Input validation and origin selection were inconsistent at the HTTP boundary.                                                                                           |
| R-011   | Opening the dashboard on SQLite executed unsupported `HOUR(created_at)` SQL; health reporting could also throw after a database probe failed. The query assumed MySQL syntax and coupled checks.                                                                                                                                                                        |
| R-012   | Clean installs could not follow one reproducible toolchain because npm/Yarn/pnpm instructions and lockfiles diverged; pnpm 11 reads overrides from workspace config. ## Investigated, not confirmed as a vulnerability

- Local path traversal is confirmed; exploitation of a symlink planted by a local OS-level writer is mitigated by canonical resolution but remains subject to filesystem TOCTOU if an attacker can concurrently mutate the storage tree.
- No client-controlled remote URL is fetched by the OTA API, so SSRF was not identified in the inspected request paths.
- CSRF is enabled for browser write methods and upload forms include CSRF tokens. CSP is disabled, and a CMS view loads Ace from a CDN; this is a hardening/availability concern rather than a reproduced injection bug.
- The audit baseline returned checksums but had no release-signing protocol. This branch adds per-software public-key registration, externally generated Ed25519 manifest signatures, server-side signature checks at signature submission/publication, and signed metadata in OTA responses. Client-side verification remains an integration requirement because no updater client source is present here. Legacy clients that ignore the envelope gain no signature protection, even when the server's signed-only policy is enabled.
- Quota checks reserve capacity transactionally. A process termination after object write leaves an expiring reservation; the next upload to that provider retries deletion using the reservation UUID. If that provider is never used again or remains unavailable, the object can persist until storage lifecycle/operator cleanup.

## Access policy applied

- Unauthenticated OTA clients can call check/latest/releases and download eligible public artifacts.
- Any active authenticated CMS user can manage versions and artifacts, including publication. Root users additionally manage accounts, storage-provider credentials, and global settings. This follows the existing `isRoot` boundary; the repository has no finer-grained role model.
- Self-profile and password changes are available to the authenticated user. Inactive users and sessions with an old auth version are rejected.
- Soft-deleting an artifact retains its object and quota usage. Archive removes it from public eligibility while retaining the object.

## Environment and dependency limits

- The checked-in test suite initially contained only `tests/bootstrap.ts`; the baseline test command reported `NO TESTS EXECUTED`.
- A disposable MySQL 8.4.11 service was started with synthetic credentials and a randomly named temporary schema. Fresh migration, additive down/reapply, legacy user preservation, remember-me token revocation, foreign key creation, and the MySQL public-release index branch passed. MySQL request-level query/concurrency behavior and production configuration were not tested.
- Dependency advisories, PostgreSQL migration checks, and container build/runtime are recorded in `docs/verification.md` with exact commands and limits.
- AWS S3, OCI, R2, MinIO, SMTP, reverse-proxy behavior, and cloud IAM remain unverified without those services. A disposable SeaweedFS integration run and local signed-protocol tests are recorded in `docs/verification.md`; they do not establish full vendor feature parity. MySQL checks cover schema upgrade behavior, not a full production-like dataset or all query plans.
